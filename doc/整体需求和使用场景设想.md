# 多人分布式组件协同开发——DSH 协同插件需求与应用场景文档

**版本**：v0.7  
**日期**：2026-09-14  
**说明**：本版将“5人”调整为“多人”这一通用表述，仅在使用场景中保留5人作为具体示例。核心仍是：**手动发布 + 按需联邦检索 + 私有隔离**，不追求实时，不自动同步。


## 一、项目背景与目标

多名开发者各自使用独立 DSH，共同开发一个分布式软件。以 5 人团队为例，调用链为：

```
组件A（成员A） → 组件B（成员B） → 组件C（成员C） → 组件D（成员D） → 组件E（成员E）
```

每人负责一个组件，组件之间存在接口调用、协议约定、版本约束。当前痛点是：组件间的契约、规范、变更、里程碑分散在各自本地，其他人开发时无法方便地获取。

**目标**：开发一个 DSH 协同插件，基于 PostgreSQL + pgvector，让每人的 DSH 能通过 IP 联邦检索其他人的知识库，按需获取组件交互信息、项目变更、里程碑等。**不追求实时，不自动同步**，所有共享都是成员主动发布的结果。


## 二、核心概念

| 概念 | 归属 | 可见性 | 说明 |
| :--- | :--- | :--- | :--- |
| **私有知识** | 个人 | 仅本人 | 内部实现、草稿、临时笔记 |
| **项目共享知识** | 个人主动发布 | 所有成员 | 组件契约、规范、变更、里程碑 |
| **联邦检索** | 插件能力 | — | 一次查询并行访问多个节点，合并结果 |


## 三、应用场景（丰富版）

### 场景 1：查询上游组件契约，直接获取接口细节

成员 C 负责组件 C，需要调用组件 B 的鉴权接口。以往他需要在群里问 B，或者翻找文档。现在他直接在 DSH 中输入：

> “组件 B 的鉴权接口怎么调用？支持哪些认证方式？”

C 的 DSH 自动触发联邦检索，并行查询本地与远端节点。成员 B 的知识库中有一条已发布的“组件 B 鉴权接口契约”，包含：

- 接口路径：`POST /api/v1/auth/token`
- 请求参数：`appId`、`appSecret`、`grantType`
- 认证方式：OAuth2 客户端模式、API Key 两种
- 错误码：`401 INVALID_CREDENTIALS`、`403 APP_DISABLED`
- 版本：v1.2，更新于 2026-09-10

DSH 返回结果，并标注来源：“来自成员 B 的组件契约库”。C 无需询问任何人，直接获得准确答案，并可将该契约加入自己的开发上下文。


### 场景 2：发布组件变更，供他人按需检索

成员 A 修改了组件 A 的订单创建接口，确认后手动在 DSH 中执行：

> `/publish 组件A 订单创建接口变更：新增 idempotencyKey 必填字段，废弃 clientToken，新增错误码 409 CONFLICT`

插件将该条目写入 A 的“项目共享”知识库，可见性标记为 `project`，并附带组件 ID、版本号、发布时间。

其他成员在后续检索“订单创建接口”时，联邦检索会返回这条最新变更。成员 B 的 DSH 在检索到后，会在回答中提示：

> ⚠️ 检测到组件 A 的接口已于 2026-09-14 变更：新增 `idempotencyKey` 必填字段，`clientToken` 已废弃。你当前组件 B 的调用代码可能受影响。

B 可以据此调整代码，而无需 A 主动通知。整个过程是“发布 → 检索 → 感知”，而非自动推送。


### 场景 3：联调前核对上下游契约

成员 B 和成员 C 准备联调。B 在 DSH 中发起：

> “核对组件 B 与组件 C 的接口契约”

插件分别检索组件 B 的契约（B 提供什么）和组件 C 的契约（C 需要什么），并生成核对报告：

- ✅ 接口路径匹配：`POST /api/v1/order/create`
- ⚠️ 组件 B 返回的 `timestamp` 是秒级，组件 C 期望毫秒级
- ❌ 组件 C 期望的错误码 `422` 在组件 B 的契约中未定义

双方根据报告调整，避免联调时才发现问题。核对完成后，可将结论发布为项目共享知识。


### 场景 4：新成员快速获取项目上下文

新成员加入团队，其 DSH 通过一次联邦检索，一次性获取：

- 项目级规范（代码风格、Git 分支策略、CI 约定）
- 各组件当前契约（A/B/C/D/E 的接口定义）
- 当前里程碑（联调完成、版本冻结、集成测试时间）
- 历史决策记录（架构选型、技术方案评审结论）

新成员无需逐个询问，即可快速进入开发状态。所有信息均来自各成员主动发布的项目共享知识。


### 场景 5：查看组件变更历史与版本演进

成员 D 想了解组件 C 的接口最近有哪些变化。他在 DSH 中提问：

> “组件 C 的接口最近有哪些变更？”

联邦检索会返回组件 C 知识库中所有标记为“变更”的条目，按时间倒序排列：

- 2026-09-12：新增 `retryPolicy` 字段
- 2026-09-08：废弃 `legacyMode` 参数
- 2026-09-01：错误码 `500` 拆分为 `5001`、`5002`

每条都标注来源、版本号、发布时间。D 可以快速了解组件 C 的演进脉络，评估对自己组件的影响。


### 场景 6：按组件、标签、类型多维检索

成员 E 在开发中遇到一个性能问题，想看看其他组件有没有类似经验。他在 DSH 中提问：

> “有没有关于连接池超时的排错记录？”

插件支持按标签、组件、知识类型过滤。检索结果可能包括：

- 成员 B 发布的“组件 B 连接池超时排查记录”（标签：连接池、超时、排错）
- 成员 D 发布的“组件 D 数据库连接池配置规范”（标签：连接池、配置、规范）

E 可以从中获得启发，或直接联系相关成员深入讨论。


### 场景 7：私有知识手动提升为项目共享

成员 D 在调试组件 D 时，记录了一份内部笔记：“使用本地缓存绕过某个限流限制的临时方案”。该笔记默认可见性为 `private`，不会出现在联邦检索中。

后来 D 确认这个方案可以通用，于是手动执行：

> `/publish 组件D 限流绕过方案（通用版）`

插件将该笔记提升为项目共享知识，其他成员在后续检索中即可获取。D 也可以选择只发布摘要，保留完整实现细节在私有库中。


### 场景 8：项目里程碑同步与提醒

团队将里程碑写入各自知识库的项目共享区：

- 2026-09-20：组件 A/B 联调完成（成员 A 发布）
- 2026-09-25：组件 C 接口冻结（成员 C 发布）
- 2026-09-30：全链路集成测试（成员 E 发布）

任何成员在 DSH 中检索“里程碑”时，联邦检索会汇总所有节点的相关记录，并按时间排序。当里程碑临近时，成员可以主动查询，但插件不会自动推送提醒——是否关注由成员自己决定。


### 场景 9：决策记录共享与追溯

团队在架构评审后，将决策记录发布为项目共享知识：

- 决策：消息队列选型采用 Kafka
- 理由：吞吐量、生态成熟度、团队熟悉度
- 参与人：A、B、C、D、E
- 日期：2026-09-05

后续任何成员对选型有疑问时，检索“消息队列 决策”即可找到这份记录，避免重复讨论。决策记录只增不改，新决策以新条目形式追加，保留历史轨迹。


### 场景 10：跨组件依赖查询

成员 E 想知道组件 E 的上游依赖有哪些。他在 DSH 中提问：

> “组件 E 依赖哪些组件？谁依赖组件 E？”

插件检索各组件契约库中声明的依赖关系，生成依赖图：

- 组件 E 依赖：组件 D（调用其数据查询接口）
- 依赖组件 E 的：无（组件 E 是调用链末端）

如果团队后续新增组件 F 依赖 E，E 可以在检索中看到新的依赖记录。依赖关系由各成员在发布契约时手动声明，插件只做聚合与展示。


## 四、功能需求（简化版）

| 编号 | 功能 | 优先级 | 说明 |
| :--- | :--- | :--- | :--- |
| F1 | 本地知识写入 | P0 | 支持私有 / 项目共享两种可见性 |
| F2 | 本地向量检索 | P0 | pgvector 相似度查询 |
| F3 | 联邦检索 | P0 | 并行查询配置的远端节点，合并结果 |
| F4 | 来源标注 | P0 | 每条结果标注节点、组件、负责人、时间 |
| F5 | 私有隔离 | P0 | 默认不检索他人私有知识 |
| F6 | 手动发布 | P0 | 将私有知识提升为项目共享 |
| F7 | 远端节点配置 | P0 | 通过设置卡片配置 IP、端口、只读账号 |
| F8 | 按组件 / 标签 / 类型过滤 | P1 | 支持按 `component_id`、`tags`、`knowledge_type` 缩小检索范围 |
| F9 | 变更 / 里程碑 / 决策记录 | P1 | 手动写入，带版本号或日期，供他人检索 |
| F10 | 版本与废弃标记 | P2 | 知识条目可带版本号，旧条目标记 `deprecated` |


## 六、非功能需求

- **性能**：联邦检索 P95 < 3 秒；远端超时 1 秒降级为仅本地结果。
- **安全**：只读账号、IP 白名单、TLS、审计日志。
- **兼容性**：适配 DSH 0.1.5-rc.2。
- **可用性**：任一远端节点故障不影响本地开发。


## 七、演进路线

**MVP（1 周）**
- 本地知识写入与检索。
- 联邦检索（支持 2-3 个节点）。
- 私有隔离与来源标注。
- 手动发布。

**V1（2-3 周）**
- 按组件、标签、知识类型检索。
- 变更记录、里程碑记录、决策记录。
- 版本标记与废弃标记。
- 节点配置界面。

**V2（可选）**
- 依赖声明与依赖查询。
- 简单冲突提示。
- 多节点结果聚合优化。


## 八、结论

核心是：**一个轻量的 DSH 协同插件，让多名开发者各自独立开发时，能按需检索到其他人主动发布的组件契约、变更、里程碑和决策记录，同时保持私有知识隔离。**  
不追求实时，不自动同步，所有共享都是成员主动发布的结果。通过丰富的应用场景，覆盖日常开发中的契约查询、变更感知、联调核对、新成员上手、历史追溯、依赖查询等需求，显著降低跨组件沟通成本。
