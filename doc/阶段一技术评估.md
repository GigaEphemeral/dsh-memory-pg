## 二、方案总结

### 2.1 架构要点

```
DSH 会话 → /memory-pg-save 命令
  → contextProvider（最近 40 条，滤 system）
  → distill（ctx.llm.stream → 三要素 JSON，分块 ≤1000 字符 ×6 块，≤8 条）
  → segment（过长递归分割/过短合并/0.92 去重/0.86 冲突）
  → persist（facts 表，workspace_id=目录名隔离；向量开→embeddings 绑定）
  → /memory-pg-search：向量关→searchAndRerank；向量开→searchHybrid（关键词+向量 RRF k=60）
```

### 2.2 四个关键设计决策

| 决策 | 内容 | 评估 |
|---|---|---|
| 检索主路径 | JSON 事实 + 关键词（CJK 二元组全表扫）+ LLM 重排；向量默认关可选开（D7） | ✅ 零外部依赖可用 |
| 提炼底座 | 三要素原子事实入库，只吸纳官方 prompt 纪律、不照搬自动压缩机制（D-M3-2） | ✅ 目标匹配，克制 |
| 主键语义 | workspaceId = cwd 目录名而非 registry UUID（D-M4-1） | ✅ 用户可读、跨实例稳定 |
| 形态 | bundle 插件（`dsh.bundle.patch` + client slot），pg 懒加载 + 设置面板驱动 | ✅ 符合 DSH 生态 |

**文档工程是亮点**：进展/任务/开发经验三件套 + 决策记录三段式 + 踩坑表 + 隐私化处理，换会话可接续——这正是本插件自身要解决的「经验延续」问题在开发流程里的实践。

## 三、待改善评估

### 🔴 P0 — 影响核心价值

#### 1. 「LLM 重排」从未真正接线——文档与实现不符

- **证据**：
  - `src/store.ts:542`：`searchAndRerank` 在 `opts.scorer === undefined` 时**默认走 `heuristicScore`**；
  - `src/commands.ts:294`：`/memory-pg-search` 调 `searchAndRerank(workspaceId, q, { limit: 10 })` **未传 scorer**；
  - `src/index.ts:449`：`CommandDeps` **没有 rerank scorer 字段**（只有 store/distillCaller/contextProvider/sessionMeta/workspaceResolver/workspaceLister/appendAssistant/memoryDir/vectorProvider）。
- **结论**：README/task.md 宣称的「关键词优先 + **LLM 重排**」主路径，生产运行里一次 LLM 重排都没发生过——一直是启发式打分（关键词分 + 标签 +0.15 + 重要性 +0.1，`src/rerank.ts:39-51`）。
- **影响**：这正是用户实测「无关信息多」的直接根因（README「当前不足 2」自述）。纯函数 `rerankHits` 写了、测了，但接线断了。
- **修复成本**：低。`rerank.ts` 接口完备，只需在 `index.ts` 给 `CommandDeps` 加 `scorer`（包装 `ctx.llm` 给 10 条候选打分），`commands.ts` 传入即可。**建议下阶段第一件事**。

#### 2. 提炼质量是主瓶颈（用户已确认）

- 单次命令提炼受上下文长度（40 条）/模型能力限制，事实粒度与覆盖率有限；`maxFacts=8` 截断会丢信息且无提示。
- Future 已列方向（prompt 增强/分轮提炼/增量提炼）但**无落地计划与验收基线**——按 technical-strategy 铁律，「下一步」没有启动条件就不算下一步。

#### 3. workspace 重命名失效（g-001）

- workspace_id=目录名的正确性代价：改名即断链（D-M4-1 自述）。已入 Future，但**无方案**（别名表/稳定 id/迁移命令三选一未定）。
- 这是「教训二」的未竟延伸，且 dsh-graph 看板 g-001 正卡在 collecting 无卡片——建议主管直接按实现方案推进而非继续收集。

### 🟡 P1 — 工程质量

#### 4. 硬编码参数未参数化

- chunkChars=1000 / maxChunks=6 / maxFacts=8 / maxChars=600 / minChars=20 / dedupScore=0.92 / conflictScore=0.86 全在 `*_DEFAULTS` 常量（好），但文档标注「待参数化」（`阶段一项目开发进展.md` §4.4.1）后 M5 已过仍未做——至少 `maxFacts`、`chunkChars` 应进设置面板。

#### 5. 记忆只有「进」没有「出」的闭环

- `load` 未实现（`src/commands.ts:310` 占位返回 error）、pressure 自动注入 v2——但 README 大目标承诺「把记忆重新注入为上下文」。检索是人工的，注入闭环缺失使「经验延续」只完成半环（D1 是设计决策，可接受，但需明确 v1.5 排期）。

#### 6. 关键词检索全表扫无索引兜底

- `searchFacts` 是 workspace 级全表扫 + 内存打分（`src/store.ts:528`），trigram 索引建了但**从未走**（D-M2-1 决策）。几十~几百条 OK，上千后必然劣化——文档自述触发条件（量级上千）已存在，但没有升级预案落地。

#### 7. 发布流程手工且重复踩坑

- scope 大小写 403/404、npm cache 沙箱、`plugin add` 不刷新 node_modules、pnpm 元数据缓存装旧版——每次发布都要重建 profile。**缺发布 checklist 或脚本化**（0.1.2 已发但 sql/schema.sql 未随包发布：files 已列未 republish）。

#### 8. 测试基础设施脆弱

- 依赖真实 PG 5433（非容器化）、vitest fork worker 需 danger-full-access、**无 CI**——80 用例全绿但无回归保障机制。

### 🟢 P2 — 工程纪律 / 度量

#### 9. token 无预算

- 272M 无里程碑预算，98% 缓存命中掩盖实际未缓存消耗 6.4M；研究性问答（compact 差距、-p 可行性）与开发未分开记账。

#### 10. 测试报告未闭环

- `测试报告/m2.md`、`测试报告/m3.md` 标注「待审批」至今未更新状态。

#### 11. 文档/代码双源一致性

- `src/schema.ts` 与 `sql/schema.sql` 双份（已人工验证一致），但**无契约守护测试**（有 theme.spec，无 schema-consistency spec）——下次改 schema 需两处同步，易漂移。

#### 12. dsh-graph 看板刚接管

- g-001 无卡片、无长期记忆，supervisor 流程刚启动，尚未跑通第一个闭环。

## 六、结论与建议优先级

**阶段一完成度：核心链路可用且用户验证过（✅），但离「经验延续」的设计承诺还有两个断点：LLM 重排未接线 + 注入闭环未做。**

下阶段最该做的三件事（按 ROI）：

1. **接上 LLM 重排**（TD-1，半天）——`index.ts` 注入 scorer，检索质量立刻逼近设计值，直接缓解「无关信息多」；
2. **给提炼建 golden-case 验收基线**——固定会话 → 预期 facts 清单，让提炼质量可度量（对应教训一），再谈 prompt 增强；
3. **dsh-graph 闭环跑通 g-001**——主管视角：判据已是实现问题，无需收集，直接派发实现 attempt（workspace 别名表方案）。
