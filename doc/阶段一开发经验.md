### 阶段实现框架

```
dsh-memory-pg/
├── package.json      # dsh.bundle.patch + dsh.client(platform web) + main:lib/index.js + pg/schemastery deps + @deepseek-ai peer
├── cordis.patch.yml  # - insert: - id: memory-pg  name: 'dsh-memory-pg'
├── tsconfig.json / tsdown.config.ts / vitest
├── src/
│   ├── prefs.ts      # 设置类型/默认值/parsePrefs 防御解析（纯逻辑，可单测）
│   ├── config.ts     # schemastery PrefsSchema（表单事实来源）
│   ├── index.ts      # Node half：settings.register + fenced 路由(settings.get/update/connection.test) + 连接测试(pg 懒加载)
│   └── client/index.tsx  # Client half：settings.section list 槽(id=SETTINGS_NS, label='dsh_memory_pg') + DB/embedding 表单 + 连接测试按钮
└── tests/prefs.spec.ts   # parsePrefs 3 用例
```

- **设置接入**：`settings.section` 是 **list 槽**（`{name,id,order,label}` 注册，一个列表项=一个设置页）→ 用户要求的「左侧列表出现」；`settings.plugin.item` 是 keyed 槽（插件卡片，另一条路径，本插件未用）。
- **fenced 路由**：settings RPC 只服务白名单 ns，客户端必须走插件自建 HTTP 路由（`/memory-pg/api/*`）读写在进程内调 seam。
- **隐私化**：本文档不写生产 `<dshhome>` 内具体业务路径；连接串保留 `127.0.0.1:54320 / postgres / *** / dsh_memory_pg`（可运行信息）。

#### D-M2-1 中文检索：不用 ILIKE 初筛，改全表扫 + keywordScore（CJK 二元组）

- **问题**：`searchFacts` 初版用 `content ILIKE '%<q>%'` 做 trigram 初筛，对英文 OK，但对中文**失效**——facts.content 是三要素空格连接（如 `用户 偏好 简洁回复`），查询 `用户偏好`（无空格）时 `ILIKE '%用户偏好%'` 0 命中。
- **思考过程（备选）**：
  - A. **保留 ILIKE 初筛 + 中文空格归一化**：查询前把 content 和 q 都去空格再比。缺点：`gin_trgm_ops` 对去空格后的长中文串效果弱（trigram 需要连续 3 字符，中文语义片段常 <3），且归一化要在 SQL 侧写表达式，可维护性差。
  - B. **全表扫 + keywordScore 内存打分**（参考实现 dsh-local-vector-memory 同构）：按 workspace 拉全部有效 facts，用 CJK 二元组（≤4 字整串、>4 字二元组）打分。缺点：无索引扫描；**但 §3.5 已论证 workspace 级记忆量小（几十~几百条），全表扫 + 内存打分足够**。
  - C. **pg_trgm similarity 操作符（`%` / `similarity()`）**：保留索引但语义是"相似度"，对短查询和中文仍不稳，且阈值难调。
- **最终决策**：选 **B**。理由：与参考实现同构（已被验证可用）；CJK 空格/分词问题彻底规避；workspace 小规模下无索引扫描可接受；trigram 索引**保留不删**（作未来大库粗筛 + `/memory-pg-search` 扩展点）。检索正确性 > 索引微优化。
- **后续提示**：若未来 memory 量级上千（§3.5 向量才真正赢的场景），应升级到「pg_trgm 粗筛 + LLM 重排」或开向量，届时重新评审。

#### D-M2-2 单测 PG 库：用 5433 `my_pgvector`（无 AGE），生产仍用 54320 `dsh_memory`

#### D-M5-4 双来源各取 limit×3 候选再做 RRF

- RRF 用排序位次而非原始分数：关键词与向量打分尺度不可比，位次天然归一；rank 太浅会丢失长尾，取 limit×3 保证深度。

## 流程教训（跨里程碑）

### 教训一：核心逻辑必须先验证、先做透，再搭外围

> 提出：2026-09-14（M3 验收反馈后，项目经理复盘）
> 适用：一切"核心 = 某条算法/某条数据管线"的项目；本项目即 dsh-memory-pg 的**提炼（distill）与拆分（segment）**。

**一句话**：做这类项目时，**第一阶段的着力点应是核心逻辑本身**——先完整想清楚"核心逻辑怎么触发、预期是什么、怎么验证"，并**让项目经理能手动触发核心逻辑验证**；而不是先把外围（骨架/设置/接线/命令框架）铺满，最后才回头验证核心。

**本次项目的实际教训（反面案例）**：

1. **核心逻辑验证起步太弱**。本项目的核心是"会话 → 提炼 → 拆分 → 入库"这条数据管线（distill + segment），但前期大量精力花在插件骨架、设置面板、命令注册、连接状态等外围；真正让**项目经理直接看到"提炼质量对不对"**的验证，直到 M3 连测才发生。
2. **因此问题暴露晚、连环返工**。核心验证滞后，导致一连串本应在早期单测/冒烟就抓住的问题拖到端到端才暴露：命令未注册（旧包未刷新）、`llm.stream` 返回 0 字符（没查 finish reason）、提炼出 8 条工具规则（没过滤 system 消息）、提炼内容不符合预期（扁平事实缺 8 节叙事框架）。每一条都是"核心链路"的问题，却是在外围都搭完后才逐个发现。
3. **缺乏"项目经理可手动触发核心验证"的入口**。核心逻辑被埋在命令/接口深处，项目经理只能通过完整会话去间接观察，无法在固定输入上复现"提炼 X 得到 Y"，判断全靠感觉。

**未来做法（固化流程）**：

1. **动手前先完整思考核心逻辑的"触发 + 预期 + 验证"三件事**：
   - **如何触发**：设计一个项目经理可**手动、最小、可重复**地触发核心逻辑的入口——固定输入（一段代表性会话/文本）→ 固定输出（提炼结果/拆分结果），不依赖真实 LLM 波动。
   - **预期**：写清楚"这段输入应该提炼出哪些记忆、拆成什么粒度、哪些不该提炼"的验收基线（golden case）。
   - **验证**：核心逻辑的**单测 + 冒烟**排进第一个里程碑的退出标准，而不是等端到端；让项目经理能一键跑"核心验证"看到通过/不通过。
2. **先做核心，再做外围**：distill/segment 这类核心管线先有可验证的最小闭环（含 mock/固定输入），确认质量达标后，再铺骨架/设置/命令/注入等外围；外围只是把已验证的核心暴露出来。
3. **核心问题验收**：核心逻辑"是不是我想要的东西"的判断，应由项目经理用**固定输入 + 固定验收基线**来做，而不是散落在完整会话里。

**关联产出**：核心提炼质量的差距分析与 8 节改造方案见 `排查用勿提交/docs/align-system-compact.md`；核心管线的可测入口建议在 M4 前补齐（固定会话 → 提炼/拆分 → 对比基线）。

### 教训二：业务标识要用"用户可理解 + 稳定"的主键，不要用运行时对象的内部 id

> 提出：2026-09-14（M4 跨项目检索实测后复盘）

**一句话**：给数据定主键/作用域标识时，**用用户能看懂、跨环境稳定、且与既有数据一致的标识**；不要图省事直接采用运行时对象的内部 UUID（如 workspaceRegistry 的 `id`）。

**本次反面案例**：M4 把 workspaceId 从 cwd 目录名改成 workspaceRegistry 的 UUID，结果新存的记忆落在 UUID、旧记忆留在目录名下，同一项目被拆成两个互斥的 workspace——用户跨项目/当前项目都搜不全。UUID 不可读（调试/核对都难）、依赖 registry 运行时状态（重启/重建可能变）、跨实例不一致（换 profile 就丢关联）。改回 cwd 目录名 + 迁移数据后统一。

**未来做法**：
1. 主键/作用域标识优先选**用户可见的稳定值**（目录名、项目名、业务编号），除非有强理由才用 UUID。
2. 若必须用内部 id，**提供"显示名 ↔ 内部 id"的映射层**，业务查询一律走显示名。
3. 换标识方案前，先盘点既有数据的主键分布（本项目用 `SELECT workspace_id, count(*) FROM facts GROUP BY 1` 一眼看出割裂）。
4. 跨实例/重启后仍要能对上——内部 UUID 若依赖运行时注册状态，慎用。

**关联**：workspace 重命名失效问题已列入 Future（需别名表/稳定 id 映射/迁移命令），正是教训二的未竟延伸。

### 教训三：命令结果的展示层要"以命令卡片为准"，不要用 append 写消息流来替代

> 提出：2026-09-14（M4 用户实测"结果消失+参数被吃"后复盘）

**一句话**：DSH 命令（`ctx.commands`）的返回 `text` 会渲染为命令卡片；**卡片就是命令结果的权威展示**。想"进对话框"而改用 `session.append` 写消息流，一旦 append 时机/显示不对，用户就什么都看不到——且写进消息流还会污染模型可见历史。

**未来做法**：
1. 命令 handler 一律**返回完整结果文本**到卡片（`{ kind:'success', text }`），不做"空卡片 + append"的替代。
2. 若确需同时展示在对话流，append 只能是**附加**（fire-and-forget，失败不影响卡片），并明确告知副作用（进入模型历史）。
3. 用户对展示层的偏好（卡片 vs 对话框）以实测反馈为准，不要替用户决定。
